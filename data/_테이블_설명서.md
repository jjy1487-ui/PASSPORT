# 여권 주세요 — 데이터 테이블 설명서

> 이 문서는 게임 데이터 테이블(시트) 21개가 **각각 무엇을 담고, 서로 어떻게 연결되는지**를 설명합니다.
> 데이터를 처음 보는 팀원이 "어디를 고쳐야 하지?"를 빠르게 찾는 것이 목표입니다.

---

## 0. 한눈에 보는 데이터 흐름 (파이프라인)

데이터는 아래 4단계를 거쳐 게임에서 쓰입니다.

```
 [1] 엑셀 (여권_정리.xlsx, 시트 21장)        ← 사람이 편집하는 "원본"
        │  임포트 툴이 읽어서 변환
        ▼
 [2] GameData.source.json                     ← 엑셀을 그대로 떠놓은 중간 파일(자동 생성)
        │  임포터가 시트별로 변환
        ▼
 [3] *.asset 테이블 21개 + GameDatabase.asset  ← 유니티가 읽는 ScriptableObject
        │  일자별로 가공
        ▼
 [4] Resources/GameData/day1.json ~ day14.json ← 게임 실행 중 실제로 읽는 파일
```

**핵심 규칙: 사람은 [1] 엑셀만 고친다.** [2][3][4]는 툴이 자동으로 다시 만들어 줍니다.
(절대 day1.json을 직접 손으로 고치지 마세요 — 다음 임포트 때 덮어써집니다.)

## 1. 테이블을 "그룹"으로 묶어서 보기

21장을 따로따로 외우면 헷갈립니다. **7개 그룹**으로 묶으면 쉽습니다.

| 그룹 | 테이블 | 한 줄 요약 |
|---|---|---|
| ① 손님 | `customer` | 누가 오는가 (사람 정보) |
| ② 진행 | `day_schedule` | 며칠 몇 번째에 누가 오는가 |
| ③ 서류 | `passport` `visa` `pcr_test` `employment_cert` | 손님이 내는 서류 내용 |
| ④ 추가 검사·정보 | `xray` `fingerprint` `news` `rule_book` | 대조에 쓰는 단서들 |
| ⑤ 대사 | `dialogue_case` `dialogue_line` | 상황별 대사 |
| ⑥ 결함 생성 | `defect_rule` `fake_value_pool` `document_requirement` | 위조 서류를 어떻게 만드나 |
| ⑦ 점수·경제 | `score_model` `character_score` `character_payout` `ending` `shop` `reward` | 점수·돈·엔딩·상점 |

---

## 2. 모든 테이블을 잇는 "열쇠(ID)"

테이블들은 **같은 ID 값**으로 서로 연결됩니다. 이 4개만 알면 관계가 보입니다.

- **`customer_id`** — 손님 1명을 가리키는 번호. 가장 중요한 열쇠.
  → `customer` → `passport`/`visa`/`pcr_test`/`employment_cert`/`xray`/`fingerprint`/`day_schedule`/`dialogue_case` 가 전부 이 번호로 연결됨.
- **`schedule_id`** — "며칠 몇 번째 손님"이라는 한 칸(슬롯)을 가리킴. `day_schedule` → `dialogue_case`.
- **`dialogue_case_id`** — 대사 상황 1개를 가리킴. `dialogue_case` → `dialogue_line`(대사 줄들).
- **`character_type`** — 손님 유형(예: 일반 고객, 관광객…). 점수/결함 테이블이 이 유형으로 연결됨.

```
customer (손님)
   ├─ passport / visa / pcr_test / employment_cert   … 이 손님의 서류 (customer_id로 연결)
   ├─ xray / fingerprint                              … 이 손님의 추가 검사 (customer_id)
   ├─ day_schedule  ─ schedule_id ─ dialogue_case ─ dialogue_case_id ─ dialogue_line
   └─ character_type ─ character_score / character_payout / defect_rule
```

## 3. 그룹별 상세 설명

### ① 손님 — `customer` (37행)
손님 한 명의 기본 신상. 모든 것의 출발점.
- 핵심 컬럼: `customer_id`(번호) · `name_kr`/`name_en`(이름) · `nationality`(국적) · `gender` · `birth_date` · `age` · `character_type`(손님 유형) · `sprite_ref`(이미지 키)
- **여기서 정한 `customer_id`로 다른 모든 손님 데이터가 연결됩니다.**

### ② 진행 — `day_schedule` (98행)
"1일차 1번 슬롯엔 3번 손님" 처럼, 며칠 몇 번째에 누가 오는지 배치표.
- 핵심 컬럼: `schedule_id` · `day`(며칠) · `slot`(몇 번째) · `customer_id`(누가) · `valid_chance`(정상 서류일 확률)

### ③ 서류 — `passport` / `visa` / `pcr_test` / `employment_cert`
손님이 제출하는 서류의 **내용(적힌 값)**. 각 행은 `customer_id`로 손님과 연결됩니다.
- `passport` (37행): `passport_no` · `name_en` · `gender` · `birth_date` · `nationality` · `issue_date`(발급일) · `expiry_date`(만료일) · `photo_ref`
- `visa` (19행): `visa_no` · `visa_type` · `nationality` · `issue_date` · `expiry_date` · `entry_type`(입국 횟수) · `memo`
- `pcr_test` (19행): `test_no` · `test_date` · `result`(결과) · `valid_until`(유효기간) · `lab_name`
- `employment_cert` (5행): `cert_no` · `company_name` · `job_title` · `issue_date` · `expiry_date`
- ※ 게임 안에서는 이 네 종류가 공통 "서류" 형태(항목 = 라벨:값)로 합쳐져 표시됩니다.

### ④ 추가 검사·정보 — `xray` / `fingerprint` / `news` / `rule_book`
서류만으로 부족할 때, **대조(크로스체크)에 쓰는 단서**들.
- `xray` (3행): `customer_id` · `result` · `detected_item`(적발물) · `hidden_location`(은닉 위치)
- `fingerprint` (3행): `customer_id` · `result` · `match_status`(일치 상태) · `matched_person`(일치 인물)
  → **xray와 fingerprint는 구조가 거의 같습니다(검사 결과 한 건). 합치기 후보입니다.**
- `news` (5행): `day` 별 뉴스. `news_title` · `news_content` · `icon_ref` → 본문에서 단서를 뽑아 손님과 대조.
- `rule_book` (6행): `day` 별 규정. `rule_title` · `rule_content` · `related_field`(관련 항목) → "이 항목은 이런 규정" 판단 근거.

### ⑤ 대사 — `dialogue_case` / `dialogue_line`
대사는 **머리(상황)** 와 **몸(대사 줄들)** 두 테이블로 나뉩니다. (1상황 → 여러 줄)
- `dialogue_case` (39행) = 상황 머리:
  `dialogue_case_id` · `schedule_id` · `customer_id` · `case_type`(상황 종류: 입장/일반 심사/…) · `character_type` · `document_type`(어떤 서류) · `doc_valid`(서류 정상 여부) · `violation_field`(위반 항목) · `game_result`(정상 승인/정상 거절/잘못 허가/잘못 거절) · `reject_count`(오거부 단계)
- `dialogue_line` (99행) = 대사 줄: `line_id` · `dialogue_case_id`(어느 상황에 속하나) · `line_order`(순서) · `speaker`(심사관/캐릭터) · `text_kr`(대사 내용)
- **항목별 위반 대사는 여기서 `document_type` + `violation_field`로 구분합니다.** (별도 설계문서 참고)

### ⑥ 결함 생성 — `defect_rule` / `fake_value_pool` / `document_requirement`
"위조/불량 서류를 어떻게 만들지"를 정하는 규칙들. (게임 디자이너·기획 영역)
- `defect_rule` (15행): 손님 유형·상황별로 어떤 서류의 어떤 항목을 어떻게 변조할지.
  `character_type` · `context` · `defect_document` · `violation_field` · `corruption_type`(변조 방식) · `target_field` · `normal_example`/`defect_example`(예시)
- `fake_value_pool` (13행): 변조할 때 넣을 **가짜 값 후보 모음**. `field`(어느 항목) · `fake_value`(가짜 값)
- `document_requirement` (4행): `day_from`~`day_to` 기간에 어떤 `document_type`이 필수인지.

### ⑦ 점수·경제 — `score_model` / `character_score` / `character_payout` / `ending` / `shop` / `reward`
판정 결과를 점수·돈·엔딩으로 환산.
- `score_model` (12행): 점수 계산용 설정값 모음. `item`(항목) · `value`(값) · `desc`(설명) — 일종의 환경설정.
- `character_score` (83행): 손님 유형·방문회차·서류상태·분기별 **점수/호칭**. 열쇠 컬럼: `character_type` · `visit_round` · `doc_state` · `defect_variant` · `branch_key` → `score` · `title`
- `character_payout` (62행): 위와 같은 열쇠로 **돈(보상)**. `branch_key` → `payout` · `bounty` · `item_drop` · `early_ending`
  → **`character_score`와 `character_payout`은 같은 열쇠(`branch_key` 등)를 공유하는 쌍둥이입니다.** (점수표 / 돈표)
- `ending` (23행): `score_min`~`score_max` 점수 구간 또는 트리거로 결정되는 엔딩. `ending_name` · `trigger_condition`
- `shop` (8행): 상점 아이템. `item_name` · `price` · `unlock_day` · `effect_type`/`effect_value`
- `reward` (7행): 특정 조건 달성 시 보상. `trigger_condition` · `amount` · `related_ending_id`

## 4. 누가 어떤 테이블을 편집하나 (역할 가이드)

| 역할 | 주로 만지는 테이블 |
|---|---|
| 시나리오/대사 작가 | `dialogue_case`, `dialogue_line`, `news`, `rule_book` |
| 레벨/케이스 기획 | `customer`, `day_schedule`, `passport`/`visa`/`pcr_test`/`employment_cert`, `defect_rule`, `fake_value_pool`, `document_requirement` |
| 시스템/밸런스 기획 | `score_model`, `character_score`, `character_payout`, `ending`, `shop`, `reward` |
| 프로그래머 | 엑셀은 거의 안 건드림. 임포터/런타임 코드만 담당 |

---

## 5. 자주 하는 작업 → 어디를 고치나 (빠른 찾기)

- **새 손님 추가** → `customer`에 행 추가(새 `customer_id`) → 그 손님 서류를 `passport` 등에 추가 → `day_schedule`에 등장 슬롯 추가 → 필요하면 `dialogue_case`/`dialogue_line`에 대사 추가
- **대사 수정** → `dialogue_line`의 `text_kr` 수정
- **위반(불일치) 항목 바꾸기** → 해당 서류 테이블의 값 + `dialogue_case`의 `violation_field`
- **점수/보상 조정** → `character_score`(점수) / `character_payout`(돈)
- **엔딩 조건** → `ending`

---

## 6. 합치기 검토 메모 (참고)

- ✅ **`xray` + `fingerprint`** → 구조가 거의 같음. 런타임은 이미 하나(`ScanData`)로 합쳐 사용 중. 소스만 합치면 깔끔.
- 🔶 `passport`/`visa`/`pcr_test`/`employment_cert` → 런타임은 공통 서류로 다루지만, 컬럼이 서로 달라 한 시트로 합치면 빈칸이 많아짐(가독성↓). 신중히.
- ❌ `dialogue_case` + `dialogue_line` → 1:다 관계라 분리가 정답. 합치지 말 것.
- 🔶 `character_score` + `character_payout` → 열쇠는 같지만 점수/돈으로 성격이 달라 분리 유지 권장.
